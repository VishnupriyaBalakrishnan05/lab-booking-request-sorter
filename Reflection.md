# Project Reflection (approximately 400 words)

The Lab Booking Request Sorter helped me understand how an AI model and ordinary Python code can work together without giving the AI complete control of an important decision. The project starts with informal messages, which may use laboratory names, short forms, dates written in words and different descriptions of morning or afternoon sessions. A language model is useful for extracting these details into a consistent JSON structure. However, I learned that the model's response cannot be trusted automatically. It may omit a field, return an invalid date, misunderstand a phrase or produce extra text. For this reason, the Python program checks every response before using it.

One important design decision was to separate extraction from decision-making. The LLM only identifies the laboratory, date, slot, number of students and a short purpose summary. Python checks whether the date is a real date, whether it is inside the semester, whether the date and student count are supported by the original message, whether the day is Sunday, whether the room has enough capacity and whether another booking already uses the same laboratory and session. This separation makes the application easier to test and explain. It also prevents the LLM from declaring a request approved or available.

The retry and fallback logic was another useful lesson. An API request can fail because of a missing key, an invalid response, a network problem or a provider limit. The program retries once and then returns a safe result with missing fields. It does not guess or treat a failed extraction as available. I also learned that API keys should be stored in environment variables and excluded from GitHub. A working application must protect credentials as well as process data correctly.

Testing showed why edge cases matter. A relative date such as “tomorrow” should not be converted into a date by guessing. An impossible date such as 31 November must fail calendar validation. A request that tries to tell the model to ignore its rules should be treated as untrusted input. The evaluation harness checks all five possible statuses using fixed examples, while the red-team cases focus on unsafe or misleading inputs.

The application is only a support tool. Even when a request is labelled available, the room has not been reserved. The lab in-charge must compare the original request, schedule and confirmed booking register before making the final decision. This human checkpoint is essential because a wrong booking can disrupt classes and practical sessions. Overall, the project improved my understanding of Python functions, dictionaries, lists, CSV files, date handling, exception handling, API integration, prompt design, testing and responsible AI use. I also learned that a system should clearly show what it can verify, what it cannot know and who is accountable for the final action.
